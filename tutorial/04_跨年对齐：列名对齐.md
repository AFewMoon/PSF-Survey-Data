# 第 4 章 跨年对齐：列名对齐

> 目标：理解 `align_survey.py` 的列名对齐——文本归一函数、组路径拆分、语义映射表与"新年份优先"的标准值选取策略。对齐的本质：**为"同一个概念在不同年份的不同拼写"建立等价类**。

## 4.1 对齐要解决什么问题

清洗后，6 年数据各有 264–573 列，直接 `pd.concat` 只有约 42 列能对上。损失来自三类差异：

1. **命名方案**：2019 的 `slug[选项]` 括号风格 vs 2020+ 的点分风格（清洗层已部分解决，遗留 `GROUP_REMAP_2019` 待处理）。
2. **组路径不一致**：同一题在不同年份路径不同——2020 `data.frameworks` vs 2023/2024 `frameworks.ml`；2020 `isolate.environments` vs 2019/2022/2023/2024 `environments.isolate`。
3. **拼写变体**：`Visual Studio Code` / `VSCode` / `vscode2`；`Amazon Web Services` / `AWS` / `AmazonWebServices`。

对齐产物的组织：

```
aligned/
├── cleaned_aligned_<year>.csv   # 列名/取值统一后的分年文件（2019–2024 共 6 份）
├── survey_2019_2024_master.csv  # 共有列纵向合并总表（185,632 行 × 154 列，含 year 列）
├── column_mapping.csv           # 列名映射表（year, original, canonical, level）
├── value_mapping.csv            # 取值映射表（year, column, original, canonical）
└── alignment_report.md
```

**映射表与数据同等重要**：`column_mapping.csv` 记录每个改名（谁改成谁、级别），`value_mapping.csv` 记录每个取值统一。任何统计口径的争议都可以回查这两张表。

## 4.2 归一函数：匹配的度量衡

判断"两个列名/取值是不是同一个东西"，需要一个归一化函数充当比较标准：

```python
PUNCT_TRANS = {
    "\u2019": "'", "\u2018": "'", "\u2013": "-", "\u2014": "-",
    "\u2026": "...", "\u00a0": " ", "\u201c": '"', "\u201d": '"',
}

def norm_text(text: str) -> str:
    """用于匹配的归一文本：统一标点、压缩空白、去尾部括号附注与冒号。"""
    s = str(text)
    for k, v in PUNCT_TRANS.items():
        s = s.replace(k, v)
    s = re.sub(r"\s*\([^)]*\)\s*$", "", s)      # 去尾部括号附注
    s = re.sub(r"\s+", " ", s).strip().rstrip(":").strip()
    return s

def norm_key(text: str) -> str:
    """匹配键：归一 + 小写 + 去所有非字母数字字符。"""
    return re.sub(r"[^0-9a-z]+", "", norm_text(text).lower())
```

两级设计各有用途：

- `norm_text`：**保留可读性**的归一，输出仍是像样的文本。用于生成标准取值文案（要展示给读者）。
- `norm_key`：**只为匹配**服务，把 `norm_text` 的结果再小写、删掉全部非字母数字。`"Visual Studio Code"` 与 `"Visual Studio Code "` 与 `"visual-studio-code"` 都归到 `visualstudiocode`。

两个细节值得推敲：

- **去尾部括号附注** `re.sub(r"\s*\([^)]*\)\s*$", "", s)`：问卷常在选项尾部加注释，如 `Python 2 (legacy)`，不同年份注释有无不定。只删**尾部**括号（`$` 锚定）而不删中间的，是因为中间括号通常是语义的一部分（如 `Not applicable (I don't use...)`）——删了会误合并两个不同选项。
- **去尾部冒号**：有的年份选项带冒号有的不带，`rstrip(":")` 吸收这个差异。

项目规范："字符串归一统一走 `norm_text()` / `norm_key()`，不要另写正则散落各处"。归一函数就是整个对齐系统的**度量衡**——度量衡不统一，后面所有的"相等"都不可信。

## 4.3 组路径拆分：把列名分成 (组， 选项)

对齐的第一步是理解每个列名的语义结构。`split_path` 把任何风格的列名拆成 `(组路径, 选项)`：

```python
def split_path(name: str) -> tuple[str, str]:
    """将列名拆成 (标准组路径, 选项)。2019 括号列先转换为点分形式。"""
    if "[" in name and name.endswith("]"):
        group, option = name.split("[", 1)
        group = GROUP_REMAP_2019.get(group.strip(), group.strip())
        return group, option.rstrip("]").strip()
    for path in sorted(KNOWN_GROUP_PATHS, key=len, reverse=True):
        if name.startswith(path + "."):
            return path, name[len(path) + 1:]
    if name in SINGLE_REMAP_2019:
        return SINGLE_REMAP_2019[name], ""
    if "." in name:
        path, option = name.split(".", 1)
        return path, option
    return name, ""
```

四种情形按优先级排列：

1. **2019 括号列**：`which_of_the_following_big_data_tool_s[Spark]` → 查 `GROUP_REMAP_2019` 把 slug 换成语义路径（`bigdata`），返回 `("bigdata", "Spark")`。`GROUP_REMAP_2019` 有 19 条，正是第 3 章预告的"截断 slug"——键如 `"what_editors_ides_do_you_use_for_python_development_in_addit"`（被 `slugify` 截到 60 字符），值是语义路径 `ide.editor`。这张表是人工整理的 2019 年语义词典。
2. **已知多级路径前缀匹配**：`KNOWN_GROUP_PATHS` 是人工维护的标准组路径清单（46 条）。注意 `sorted(..., key=len, reverse=True)`——**最长优先**。原因：路径有前缀嵌套关系（`environments.isolate` 包含前缀 `environments`），若短的先匹配，`environments.isolate.Pyenv` 会被错拆成 `("environments", "isolate.Pyenv")`。最长优先保证组路径整体吃准。
3. **2019 单选题**：`SINGLE_REMAP_2019` 只有一条（`for_what_purposes_do_you_mainly_use_python` → `main.purposes`），因为其余单选已在清洗层由 `SINGLE_COL_ALIASES` 处理。
4. **兜底**：点分列按第一个点切分；无点列自成一组、无选项。

拆分之后统一应用组路径正典表：

```python
# 跨年组路径冲突的统一标准（适用于所有年份）
GROUP_PATH_CANON: dict[str, str] = {
    "data.frameworks": "frameworks.ml",
    "isolate.environments": "environments.isolate",
}
```

这张小表只处理"两个年份对同一道题用了不同顺序的路径词"。方向的选择有讲究：`frameworks.ml`（2023）胜过 `data.frameworks`（2020）、`environments.isolate`（2019/2022/2023）胜过 `isolate.environments`（2020）——都是**多数年份的写法**胜出，保证重命名影响面最小。

## 4.4 等价类：变体收集与标准名生成

`align_columns` 的核心是一个双层字典，为所有年份的所有列构建**等价类**：

```python
def align_columns(dfs: dict[int, pd.DataFrame]) -> tuple[dict[int, pd.DataFrame], pd.DataFrame]:
    # key=(标准路径, 归一选项键) -> {"canon": 标准选项文本, "canon_year": int, "by_year": {y: [原始列]}}
    variants: dict[tuple[str, str], dict] = {}
    for year in YEARS:
        for col in dfs[year].columns:
            path, option = split_path(col)
            path = GROUP_PATH_CANON.get(path, path)
            entry = variants.setdefault((path, norm_key(option)), {"canon": "", "canon_year": -1, "by_year": {}})
            entry["by_year"].setdefault(year, []).append(col)
            if option:
                idx = YEARS.index(year)
                if entry["canon_year"] <= idx:          # 新年份优先
                    entry["canon"] = canonical_option(option) or entry["canon"]
                    entry["canon_year"] = idx
```

读懂三个设计决策：

**（a）等价类的键是 `(标准路径, norm_key(选项))`。** 同一组的所有拼写变体（`VSCode`、`vscode2`、`Visual Studio Code`）归一后落进同一个键，天然形成"这组列是同一道题的同一个选项"的等价类。`by_year` 记录每一年对应的原始列名（可能不止一个——同一年里也可能有变体列）。

**（b）标准选项文本（`canon`）"新年份优先"。** `canon_year` 记录当前标准文本来自哪一年，`entry["canon_year"] <= idx` 意味着后处理的年份（`YEARS` 列表从 2019 排到 2024）总是覆盖前者，最终 `canon` 是**最新年份**的写法。为什么？问卷措辞随时间演进，最新版本通常是最规范、最完整的表述（例如把 IDE 选项从截断的 `PyCharm Professional Editi...` 改成全名）。取旧写法会让标准名停留在上游早已废弃的拼写上。

**（c）标准名拼接。**

```python
std_name[(path, okey)] = f"{path}.{entry['canon']}" if okey and entry["canon"] else path
```

有选项的等价类标准名为 `路径.标准选项`（如 `ide.editor.Visual Studio Code`），单选题只有路径。**标准名的取值文本来自最新年份，但标准名一旦确定，所有年份的对应列都改用它**——这就是跨年可比的来源。

`canonical_option` 在生成标准文本前先过同义词表：

```python
def canonical_option(option: str) -> str:
    key = norm_key(option)
    if key in OPTION_ALIASES:
        return OPTION_ALIASES[key]
    return norm_text(option)
```

`OPTION_ALIASES`（19 条）处理"缩写 vs 全称"这类**归一救不了**的差异：`vscode`、`vscode2`、`visualstudiocode` 三个归一键都指向 `Visual Studio Code`；`aws`/`amazonwebservices` → `AWS`；`azure`/`microsoftazure` → `Microsoft Azure`；还有 `devops(s)` 复数差异的条目。注意方向约定：**映射目标是"最新年份使用的文本"**，与（b）的新年份优先一致。

## 4.5 重命名与冲突消歧

确定标准名后，回到每个年份逐列改名：

```python
    mapping_rows: list[dict] = []
    aligned: dict[int, pd.DataFrame] = {}
    used = {y: Counter() for y in YEARS}
    for year in YEARS:
        renames: dict[str, str] = {}
        for col in dfs[year].columns:
            path, option = split_path(col)
            path = GROUP_PATH_CANON.get(path, path)
            new = std_name[(path, norm_key(option))]
            level = "exact" if col == new else "normalized"
            if used[year][new]:
                new = f"{new}__dup{used[year][new]}"
            used[year][new] += 1
            renames[col] = new
            if col != new:
                mapping_rows.append({"year": year, "original": col, "canonical": new, "level": level})
        aligned[year] = dfs[year].rename(columns=renames)
    return aligned, pd.DataFrame(mapping_rows)
```

- **`level` 字段**区分改名级别：`exact`（原名即标准名，无需改）与 `normalized`（经归一/映射才统一）。报告按年统计改名数，读者能一眼看出哪一年命名最"离群"（实际是 2019 年最多）。
- **`__dup` 后缀机制第二次出现**：若同一年内两个原始列归到同一标准名（罕见但可能——如同一年两个变体列），追加后缀消歧，与清洗层的同名约定一致：**带 `__dup` 的列内容不同，禁止合并**。
- 只有 `col != new` 的行才进映射表——映射表只记录"发生过的变化"，保持精简。

## 4.6 验证对齐效果：共有列数

对齐成功的最直接指标是**跨年共有列数**：

```python
common = sorted(set.intersection(*(set(dfs[y].columns) for y in YEARS)))
```

实际数字：对齐前 42 列，对齐后 **153 列**（另有 `year` 列共 154 列），总表 185,632 行；列名映射 382 条、取值统一 109,745 条。报告输出每一年"总列数 / 落在共有列中的列数"，审读时关注两点：

1. 共有列增量是否与 `GROUP_PATH_CANON` + `GROUP_REMAP_2019` 的预期覆盖一致；
2. 某一年"落入共有列"的列数异常偏少 → 该年有大量列名没被任何映射表覆盖，通常是新题或拼写变体，需要扩充映射表。

这也是本仓库的开发节奏：**扩展对齐 = 改顶部映射字典 → 重跑两个脚本 → 核对报告统计**。逻辑永远不改，只改数据（映射表）。

## 4.7 本章要点

- 对齐的本质是为同一概念的多种拼写建等价类，键为 `(标准路径, 归一选项键)`。
- `norm_text`/`norm_key` 是全系统的度量衡，禁止散落另写。
- `split_path` 四级优先：括号列 → 最长已知路径 → 单选映射 → 兜底切分。
- 标准值"新年份优先"，`OPTION_ALIASES` 兜住缩写类差异。
- 最长优先匹配防前缀嵌套误拆；`GROUP_PATH_CANON` 方向取多数年份写法。
- 映射表（column/value_mapping.csv）与数据同等重要，是统计口径的最终依据。

### 参考答案

**4.1** 前者：去尾部括号附注 → `PyCharm Professional Edition` → 小写去非字母数字 → `pycharmprofessionaledition`。后者：`\u2026 → "..."` → `pycharmprofessionaledition...` 再去掉点 → `pycharmprofessionaledition`。同一等价类。括号附注由 `norm_text` 的尾部括号规则吸收，省略号由 `PUNCT_TRANS` 吸收。对照 `OPTION_ALIASES`，`pycharmprofessionaledition` 还会进一步映射到 `PyCharm Professional Edition` 标准文本。

**4.2** 拆成 `("environments", "isolate.Pyenv")`。暴露点：构建等价类时 `(path, okey)` 变成 `("environments", "isolatepyenv")`，与真正的 `environments` 组选项（如 `environments.Venv`）永远合不上一类，`environments.isolate.Pyenv` 独自一类、标准名生成为 `environments.isolate.Pyenv`（碰巧还原原名）。后果更隐蔽的形态是：若存在真列 `environments.Pyenv`（不同题），两者被并进同一等价类，**语义不同的列被合并**。所以最长优先不是性能优化而是正确性要求。

**4.3** 数据本身（清洗产物）不变；变化在标准列名——总表列头从 `frameworks.ml.*` 变成 `data.frameworks.*`，`column_mapping.csv` 的 canonical 值相应反转。统计数字不变（合并等价类相同），但：a) 标准名偏离多数年份写法，更多列需要重命名，映射表膨胀；b) 与 `KNOWN_GROUP_PATHS`、绘图脚本 `MULTI_GROUPS` 里引用的组名失去一致，下游引用会断。选方向考虑：多数年份写法、下游既有引用、语义自然度（`frameworks.ml` 比 `data.frameworks` 更贴近官方 2023 文案）。

```python
import pandas as pd
from align_survey import split_path, KNOWN_GROUP_PATHS

def audit_paths(path_fmt: str = "aligned/cleaned_aligned_{}.csv") -> dict[int, list[str]]:
    unknown: dict[int, list[str]] = {}
    for year in range(2019, 2025):
        df = pd.read_csv(path_fmt.format(year), encoding="utf-8-sig",
                         keep_default_na=False, nrows=0)
        unknown[year] = [
            col for col in df.columns
            if not any(col.startswith(p + ".") for p in KNOWN_GROUP_PATHS)
            and "[" not in col
        ]
    return unknown
```
