# 第 3 章 数据清洗：列名规范化与多选题处理

> 目标：精读 `clean_survey.py` 的列名规范化（两种表头风格统一）、多选二值化、数值类型转换三步。这是清洗管线里逻辑密度最高的部分。

## 3.1 两种风格的表头，一次统一

第 1 章已确认：2019 年表头是 `选项:完整问题文本`，2020–2024 是 `前缀.题目.选项`（列数从 2020 年的 264 一路涨到 2024 年的 573）。`rename_columns` 按年份选用不同策略：

```python
def rename_columns(df: pd.DataFrame, style: str) -> tuple[pd.DataFrame, dict[str, str]]:
    """列名规范化，返回 (新df, 旧->新映射)。"""
    mapping: dict[str, str] = {}
    used = Counter()
    for col in df.columns:
        if col == "response_id":
            new = col
        elif style == "question":                          # 2019：拆 问题:选项
            m = re.match(r"^(.*?):(.*)$", col, flags=re.S)
            if m and len(m.group(1)) <= 80 and m.group(2).strip():
                value_part, question_part = m.group(1), norm_ws(m.group(2))
                group_slug = QUESTION_GROUP_ALIASES.get(question_part.lower())
                if group_slug:
                    new = f"{group_slug}.{norm_ws(value_part)}"       # 已知题 → 语义前缀
                else:
                    new = f"{slugify(question_part)}[{norm_ws(value_part)}]"  # 未知题 → slug[选项]
            else:
                q = norm_ws(col).lower()
                new = SINGLE_COL_ALIASES.get(q, slugify(q))           # 单选题
        else:                                                # 2020-2024：仅规范空白
            new = norm_ws(col)
        if used[new]:
            new = f"{new}__dup{used[new]}"                   # 同名冲突消歧
        used[new] += 1
        mapping[col] = new
    return df.rename(columns=mapping), mapping
```

逐块拆解：

**（a）正则 `^(.*?):(.*)$` 拆分 `问题:选项`。** `.*?` 是非贪婪匹配：问题文本里也可能有冒号（如 `Python 2: Do you use...`），非贪婪保证在**第一个**冒号处切分。反过来若用贪婪 `^(.*):(.*)$` 会在最后一个冒号处切分——对 "选项:问题" 格式是错的。`flags=re.S` 让 `.` 也匹配换行（列名里可能含换行）。

**（b）长度护栏 `len(m.group(1)) <= 80`。** 防御性判断：冒号左边超过 80 字符，几乎肯定不是"选项"而是一个含冒号的完整问题文本（某列本身就是个单选题，问题里带冒号）。不做这个判断，会把整段问题文本误当选项拼进列名。

**（c）语义映射表。** 识别出来的问题文本经 `QUESTION_GROUP_ALIASES` 查表：

```python
QUESTION_GROUP_ALIASES: dict[str, str] = {
    "what other language(s) do you use?": "other.lang",
    "for what purposes do you mainly use python?": "main.purposes",
    "which database(s) do you regularly use, if any?": "database",
    # ...共 11 条
}
```

命中的题（都是多选）获得语义化前缀：`Django:What web frameworks...` → `web.Django`；未命中的单选题走 `SINGLE_COL_ALIASES`（5 条，如 `is python the main language...` → `is.python.main`）；其余未知列降级为 `slugify`。

**（d）`slugify`：把任意文本压成安全标识符。**

```python
def slugify(text: str, max_len: int = 60) -> str:
    s = re.sub(r"[^0-9a-z]+", "_", text.lower()).strip("_")
    return s[:max_len].rstrip("_")
```

小写、非字母数字全部换成下划线、截断到 60 字符（2019 年问题文本动辄 100+ 字符，不截断会导致跨年组路径匹配困难）。截断有歧义风险——两个长问题截断后可能同 slug——这正是对齐管线 `GROUP_REMAP_2019` 里那些以 `_in_addit` 结尾的键的由来（第 4 章）。

**（e）`__dup` 消歧。** `used` 计数器保证新列名全局唯一：第二个同名列追加 `__dup1`。关键约定：**含 `__dup` 后缀的列是同名冲突列，内容彼此不同，绝不可合并**（AGENTS.md 明文警告）。典型来源：2019 年两个不同问题在 slug 化后撞名，但两列数据完全独立。

`rename_columns` 返回映射字典而非只改名字——映射立即进入清洗报告（`renames` 字段），实现"每个改名可追溯"。

## 3.2 多选题二值化：怎么"认出"一列是多选列

原始多选列的取值形态是 `''`（未选）/ `'PostgreSQL'`（选中）——选项文本重复出现在列名和列值里。二值化就是把它变成 `0/1`：

```python
def binarize_multiselect(df: pd.DataFrame) -> tuple[pd.DataFrame, list[str]]:
    """多选二值列归一为 0/1。

    判定规则（两种命名风格通用）：非缺失取值基本只有一种、且该值出现在列名中
    （前缀列取最后一个'.'后的文本，括号列取[...]内文本）的列视为多选列。
    """
    converted: list[str] = []
    df = df.copy()
    for col in df.columns:
        m = re.search(r"\[(.+)\]$", col)
        option = m.group(1) if m else (col.rsplit(".", 1)[-1] if "." in col else "")
        if not option:
            continue
        vals = df[col][df[col] != ""]
        if vals.empty:
            continue
        distinct = set(vals.unique())
        if len(distinct) == 1 and distinct.pop().lower() == option.lower():
            df[col] = (df[col] != "").astype(int)
            converted.append(col)
    return df, converted
```

设计的精妙处在**判定规则**。没有人工标注哪些列是多选列（6 年数据、264–573 列，手工标注脆弱且不可维护），管线用三条特征自动识别：

1. **从列名提取"期望选项"**：括号列取 `[...]` 内文本（2019 风格），点分列取最后一个 `.` 后的文本（2020+ 风格）。
2. **非空取值只有一种**：多选二值列的本质是"勾选时填选项文本"，所以非空值集合大小应为 1。
3. **该取值与列名中的选项文本一致**（大小写不敏感）：防止碰巧只有一种取值的单选题被误转（如某题所有人都答了 "Web development"——它满足条件 2 但不满足 3，因为列名不是选项文本）。

两个防御分支：

- `vals.empty`（整列已空）：跳过，不转——此时无法验证取值形态，且全 0 列与全 1 列的转换都无意义。
- `set(distinct)` 大小写不敏感比较：源数据偶见 `VSCode` vs 列名 `vscode` 的情况，先按语义判定为多选列，大小写差异留给对齐阶段归一。

**为什么不先列清单再二值化？** 显式清单（"这 300 列是多选"）可读但脆弱：新增年份、上游加选项都会漏。自动判定+报告（`binarized` 计数、`bin_col_names` 清单进报告）既鲁棒又可审计——审计时从报告反查"哪些列被转了"，比对数量是否合理即可。

## 3.3 数值类型转换：_int64 / float64 / 空串三态

```python
def convert_numeric(df: pd.DataFrame) -> tuple[pd.DataFrame, list[str]]:
    converted: list[str] = []
    df = df.copy()
    for col in df.columns:
        if col == "response_id":
            df[col] = pd.to_numeric(df[col], errors="raise").astype("int64")
            converted.append(col)
            continue
        if not pd.api.types.is_object_dtype(df[col]):
            continue                      # 已是数值/布尔等类型，跳过
        vals = df[col][df[col] != ""]     # 只检查非空取值
        if vals.empty or not bool(vals.str.fullmatch(r"-?\d+(\.\d+)?").all()):
            continue
        num = pd.to_numeric(vals)
        if (num == num.astype("int64")).all():
            df[col] = pd.to_numeric(df[col].replace("", None)).astype("Int64")
        else:
            df[col] = pd.to_numeric(df[col].replace("", None)).astype("float64")
        converted.append(col)
    return df, converted
```

要点逐条：

- **`response_id` 强转**：ID 列是主键，`errors="raise"`——若 ID 出现脏值直接报错停机，让问题暴露在管线入口而不是下游静默烂掉。主键完整性用 fail-fast，数据列用宽容转换，两种策略并存是有意的。
- **判定条件是 `fullmatch(r"-?\d+(\.\d+)?")`**：整列**非空取值**全部匹配"可选负号+数字+可选小数"才转换。一个混进来的 `"3.5万"` 就会让整列保持字符串——宁可少转不错转，字符串列永远可以事后转，转错的数值列很难救回来。
- **空串参与转换时先 `replace("", None)`**：空串不是数值，必须先转成 `None`（pandas 可空类型的缺失）再 `to_numeric`。
- **`Int64`（大写 I）是 pandas 的可空整型**。普通 `int64` 不能存缺失（NaN 会强制升为 float，把整数 25 变成 25.0）；可空 `Int64` 保证"整数语义 + 缺失可用"共存。这里隐含了与全局约定的一个衔接：**在内存中缺失呈现为 pandas 的 NA，落盘时由 `to_csv` 写回空串**——外部文件约定（缺失=空串）与内存表示（可空类型）通过序列化边界隔离，互不干扰。
- **`s.nunique(dropna=False) > 60` 的自由文本保护在取值对齐阶段（第 5 章）才出现**；数值转换不设此类阈值，因为 `fullmatch` 本身已经是足够严的门槛。

## 3.4 一步一报告：类型转换也要可审计

`clean_year` 把 `binarized` / `numeric` 数量与 `bin_col_names` / `num_col_names` 清单全部写进报告。审读报告时的两个经验校验：

1. **多选归一列数 ≈ 该年多选题列数**。六年的实际值分别是 218 / 227 / 356 / 344 / 417 / 492（2019→2024），与列数膨胀的节奏一致；若某年 `binarized` 明显偏少，优先怀疑上游把多选列导出成了带引号的复数取值（如 `"Django;Flask"`），那是取值形态的问题，要在 `clean_cell` 之前处理。
2. **数值列应是"真数值语义"的列**：`response_id`、可能的收入/年限等。若发现某个明显是分类的列被转成数值（如用 `1/2/3` 编码的选项），说明它其实是有序单选题——转换无害但分析时要按类别处理，应在报告中注明。

## 3.5 本章要点

- 表头统一的核心是"已知问题查表、未知列降级 slugify"，配长度护栏与同名消歧。
- 非贪婪正则 + 长度护栏是拆 `问题:选项` 的安全组合。
- 多选列自动判定三特征：列名含选项、非空取值单一、两者一致。
- `Int64` 可空整型解决"整数 + 缺失"共存；落盘由 `to_csv` 回写空串维持全局缺失约定。
- 类型转换 fail-fast（主键）与宽容（数据列）并用；一切转换进报告。

### 参考答案

**3.1** 本例只有一个冒号，两种写法结果相同（`("Django", "What web frameworks...")`）。差异出现在**有多个冒号**的列名上：非贪婪 `.*?` 在第一个冒号处切分（左组最短），贪婪 `.*` 在最后一个冒号处切分（左组最长）。对 "选项:问题" 格式应取第一个冒号——选项文本里不会有冒号，而问题文本可能含（如 `Python 2: ...`）。通用准则：**两侧中更"干净"、更不可能含分隔符的一侧决定用非贪婪（它靠左时）或贪婪（它靠左且应吃到最右时）**。

**3.2** `distinct = {'PostgreSQL', 'postgresql'}`，长度为 2，条件 `len(distinct)==1` 不成立，该列**不会被转换**，静默留在字符串列。这暴露的取舍：严格"单值"判定保证了不会误转（把单选题错当多选转成 0/1），代价是取值不纯的多选列被漏掉——漏转是"保守失败"，可以从审计报告（练习 3.3 的函数）发现并人工确认；误转则是"激进失败"，错误直接污染数据。宁可保守。大小写问题最终由对齐阶段 `norm_key` 兜底（列名层面统一），取值层面因二值化漏转而保留原文——所以此类列会在对齐报告的取值映射里出现。

**3.3** 参考实现：

```python
def audit_multiselect(df: pd.DataFrame) -> list[str]:
    suspects: list[str] = []
    for col in df.columns:
        if col == "response_id" or not pd.api.types.is_object_dtype(df[col]):
            continue
        m = re.search(r"\[(.+)\]$", col)
        option = m.group(1) if m else (col.rsplit(".", 1)[-1] if "." in col else "")
        if not option:
            continue
        vals = df[col][df[col] != ""]
        if vals.empty:
            continue
        distinct = set(vals.unique())
        if len(distinct) == 1 and distinct.pop().lower() == option.lower():
            suspects.append(col)   # 形态符合多选列但仍是字符串 = 漏转
    return suspects
```

跑在 `cleaned_*.csv` 上，若返回空清单说明二值化无遗漏。

**3.4** 该列非空值 `{"1","3"}` 全部匹配整数正则，且 `(num == num.astype("int64")).all()` 成立，走 `Int64` 分支；落盘 `to_csv` 后缺失写为空串。小写 `int64` 是 numpy 不可空整型：含 `None` 的列在 `astype` 时抛 `TypeError: cannot convert NA to integer`——pandas 不允许整型存 NA，只能升 float 或用可空 `Int64`。

**3.5** 选 c) 上游修复为首选（治本，且修复后老管线零改动）。上游不可控时选 a)：在 `clean_cell` 之前加一步"拆分多选取值"（把 `"Django;Flask"` 拆成行内标记再与列结构重组），保持"清洗后数据 = 二值列"的下游约定不变。b) `get_dummies` 看似省事，但绕过了管线的列名/审计体系：生成的列名不进 `column_mapping`、不进清洗报告，破坏可追溯性，且需要事后手工对齐列名。原则：**宁可管线多一步，不让数据绕过管线**。
