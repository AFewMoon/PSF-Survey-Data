# 从 153 列到 110 列：跨年对齐的两条路

**组会汇报 · 2026-11-06 · 汇报人：曾子睿**

---

## 01 封面：同一张表，两种做法

【一句话】2019–2024 六年的 PSF 调查数据，先用人工映射拼出一张 153 列的总表，再让本地 4B 模型独立走一遍，看它能替掉哪一段。

【要点】

- 清洗后 185,632 行、6 个年份、200–570 列不等的宽表
- 人工路线：跨年共有列 42 → 153，重命名 382 条，取值统一 109,745 条
- LLM 路线：`qwen3.5:4b` + Ollama，得到 110 列、185,586 行
- 今天不评"哪条路更强"，只回答"哪一段能交给模型"

口播：这次汇报分两半。前半段是已经交付的人工对齐，42 个跨年共有列扩到 153 个；后半段是这两周试的本地小模型，独立跑完清洗和对齐，拿到 110 列。两条路差 43 列，但重叠的部分几乎一样。我想讲清楚这个"差"和这个"一样"分别意味着什么。

【来源】`README.md`；`aligned/alignment_report.md`；`llm/reports/alignment_report.md`

## 02 一页看清成果

【一句话】人工路线交付了完整总表；LLM 路线少 43 列，但在两边都有的 105 列上，数值几乎逐格一致。

【要点】

- 人工：153 列、185,632 行、382 条列名映射、109,745 条取值统一
- LLM：110 列、185,586 行、305 条重命名、31 个选项同义簇、5,217 条取值统一
- 重叠：105 列同名匹配，Jaccard 66.5%
- 一致：105 列非空率差 ≥1pp 的为 0 条；同主题 12 条对比里只有 2 条差 0.1pp

口播：先看总数。人工这边 153 列、18.56 万行；模型那边 110 列、18.56 万行，行数只差 46。列数差 43，拆开看是 48 列只有人工有、5 列只有模型有、105 列两边都有。关键在最后这个 105：非空率差异超过 1 个百分点的，一条都没有。

## 03 手搓对齐怎么走

【一句话】先统一"题在哪一组"，再统一"列叫什么"，最后统一"选项怎么写"，顺序反了会白干。

【要点】

1. **文本归一**：大小写、全半角、弯直引号、`etc_` → `etc.`，只做确定性替换
2. **组路径重映射**：`isolate.environments.Docker` → `environments.isolate.Docker`；2019 的长问句 `what_other_language_s_do_you_use[...]` → `other.lang.*`
3. **同义词表**：`systems administration` → `System administration`；`OS-provided Python (via apt-get, yum, homebrew, etc_)` → `OS-provided Python`
4. **重名去重**：新名字撞车就回退确定性归一，再撞就加 `__dupN`
5. **取值统一**：只处理"同一选项的不同写法"，共 109,745 条
6. **取交集**：六年都存在的列才进总表，得到 153 列

口播：手搓这条路，写代码不难，难在定顺序：先归组，再改列名，最后才动取值。顺序反了，改好的名字会被后面的归一化冲掉，白干一遍。

【图】`figures/f2_mapping_scale.png`（人工 382+109,745，LLM 305+5,217）

【来源】`aligned/alignment_report.md` 重命名示例；`align_survey.py`

## 04 手搓的代价

【一句话】153 列不是一次写成的，2019 一年就改了 201 个列名，成本集中在"第一次遇到新题型"。

【要点】

- 分年重命名：2019 **201**、2020 31、2021 48、2022 43、2023 25、2024 34
- 2019 是格式最乱的一年：长问句做列名、选项挤在方括号里、大小写混用
- 2023/2024 题干改写，同义词表要跟着补（`how.involved` 的整句变体）
- 模型归并撞名 25 处（2019 九处、2021/2022 各五处、2023/2024 各三处），已回退确定性归一；最终总表仍有 15 个 `__dup` 列
- 好处：每一步都有 diff，可解释、可复现；坏处：新一年多出上百列时，第一年最费人

口播：代价也在这。2019 一年改了 201 个列名，后面五年加起来才 181 个——那年的列名是整句问句，等于没有命名规范。这套映射表是一年一年撞出来的，好处是能 diff、能回滚，坏处是明年再来新题，第一年还得人肉趟一遍。

【来源】`aligned/alignment_report.md` 分年统计；`llm/reports/alignment_report.md` 校验提示

## 05 小模型怎么试

【一句话】模型不碰数据，只输出可校验的决策 JSON；候选由人工词表和数据证据给出，模型只在边界上回答"是不是同一个"。

【要点】

- **输入是画像，不是原始表**：列名、非空率、唯一值数、top 值、长度分布；自由文本列脱敏，只给长度
- **组路径三段式**：证据快对齐（选项重合 ≥0.60 且领先第二候选 ≥0.10，不问模型）→ 证据不够的逐对问"是否同题" → 剩下的从人工词表 84 条候选里选写法，缺省 `keep`
- **选项/取值两段式**：`norm_key` 确定性合并 → 候选对逐对判断 → 并查集聚簇 → 按人工词表统一写法（78 处）
- **护栏**：Yes/No 占比 ≥0.60 禁改道版本类路径、`multi_level` 与 `multi_option` 题型冲突拒合、多选取值 Jaccard <0.20 拒合、结构不得重复拼接、簇 ≤4 项且 ≤50%、删行 ≤60%、删列 ≤20%
- **缓存**：304 个决策文件，sha256 键；首次全量约 30 分钟，命中缓存 2.7 分钟
- **口径**：2023/2024 的人工映射不进提示词，只用于对账
- **结果**：20 处组路径改道、31 个同义簇、162 对判定（接受 34 对）、5,217 条取值统一

口播：模型这部分，我刻意让它"只动嘴不动手"：看到的是列画像，输出的是 JSON，真正执行的是 Python。我改了一版做法：不再让模型"给标准路径"，先让代码拿证据定——某组的选项和人工某条路径重合 0.93，就直接对齐，不问模型；证据不够的才逐对问"这两条是不是同一道题"，它只答 a 或 b；剩下的在人工词表里选写法。选项和取值同理，先合并完全相同的，剩下逐对判同义，最后由词表定写法。4B 判断很稳，可一旦要它"生成"，就整组塌缩或自造路径。

【来源】`llm/README.md`；`llm/reports/alignment_report.md`；`llm/decisions/` 计数

## 06 两条线对账

【一句话】覆盖差 43 列，重叠的 105 列数值几乎一样。名字对了、语义错了，是更难发现的那类问题。

【要点】

- 并集 158 = 105 匹配 + 48 仅人工 + 5 仅 LLM
- 差距集中在跨年改名的题：`develop.for.cloud`（2019 叫 `run.in.cloud`）、`orm`（2019 叫 `ide.databases`）、`unittesting`、`other.purposes` 整族
- 105 个匹配列，非空率差 ≥1pp 的 **0 条**
- 同主题 12 条对比，只有 `other.lang.C/C++` 差 0.1pp（28.1% vs 28.2%）
- 行数：2021 差 23（23,201 vs 23,178）、2022 差 23（23,009 vs 22,986），其余四年一致
- 口径：2023/2024 人工映射未进提示词，105 是留出测试成绩
- 反例：`is.python.main → ide.python_version`（改造前），路径合法、六年一致，但语义是"是否以 Python 为主"；现在取值指纹护栏直接拒掉

口播：两边都有的 105 列，非空率没有一条差过 1 个百分点。列集合的 Jaccard 是 66.5%，剩下的差距基本都在跨年改名题上：云开发那道题 2019 叫 `run.in.cloud`，后来叫 `develop.for.cloud`，没有共同词，模型不敢并。另一种错更难发现：改造前 `is.python.main` 被六年如一日映射成 `ide.python_version`，路径完全合法，格式护栏抓不到，四个真版本列变成 `__dup`。现在这条会被"取值是 Yes/No 就不能进版本题"直接拦住。

【图】`figures/f3_parity.png`（105 / 48 / 5 与三条一致性指标）

## 07 结论与下一步

【一句话】交付继续走人工映射；模型用来出候选、做交叉核对、写解释，定稿仍然要人。

【要点】

- **人工**：确定性强、可解释、可复现；成本在映射表维护，2019 年一次 201 条
- **LLM**：逐对判断（同题、同义）可用，长题干和新列名的语义判断可用；一旦要求"生成"标准路径或整组聚类就不可用；组路径仍会犯"结构合法、语义错误"的错，靠取值指纹兜
- **下一步**
  1. 给跨年改名题补名称证据（`develop.for.cloud`、`orm`、`unittesting` 仍判 `keep`）
  2. 被拒映射进人工确认队列，确认后写回规则管线映射表
  3. 统计与图表跟着对齐产物自动重跑
- **边界**：叙述可以让模型润色，数字必须回到 CSV

口播：所以两条路可以并存。人工那条继续交付，模型这条我打算用在新一年的候选映射、对账的第二双眼睛、以及把差异写成解释。它最不能信的，恰恰是它写得最顺的那部分：parity 报告里模型自己写"规则管线更可信"，论据是"开发环境类信息更少"——可 `environments.isolate` 三列里两列都在，它只是猜。叙述可以交给模型，数字必须回到 CSV。

【来源】`llm/reports/parity_report.md` 模型解读；`llm/reports/alignment_report.md` 校验提示

## 附录 A：可能被追问的五个问题

**1. Jaccard 只有 66.5%，为什么还说两条线一致？**

Jaccard 衡量列集合重叠，不衡量同名列的取值。剩下 43 列的差距集中在跨年改名的题（`develop.for.cloud`、`orm`、`unittesting`）和个别选项写法上，不是算错。一致性要看交集：105 个同名列，非空率差 ≥1pp 的 0 条。

**2. 非空率差是怎么算的？分母是什么？**

逐列算非空单元格占该年总行数的比例，再取两年差值的绝对值。2021/2022 两边行数各差 23，但没有把任何一列推过 1pp。

**3. 5,217 条取值统一，是不是虚高？**

这个数字数的是受影响的单元格，与人工那 109,745 条同口径。去重后只有 25 条不同映射，其中 21 条是版本号字形归一（`Python 2.3` → `Python 2_3`），真正的词义归并是 `Eclipse with PyDev → Eclipse + Pydev` 这一类。汇报时说"5,217 条单元格"比说"5,217 条映射"准确。

**4. 2021/2022 各差 23 行，差在哪？**

LLM 多删了 23 条重复行：2021 删 438 条、人工删 415 条；2022 删 302 条、人工删 279 条。具体是哪一列参与去重导致的口径差，还没追到列级，先记为待查。

**5. 明年再来一版数据，先做哪一步？**

先跑 LLM 出组路径候选，再人工审 diff。三段式的顺序不要改：先让代码拿证据定，剩下的才问模型，问也只让它答"是不是同一个"；也不要直接采信模型写的差异解释。
