**组会汇报 · 2026-11-06 · 汇报人：曾子睿**

## 01 封面：同一张表，三种做法

【一句话】2019–2024 六年的 PSF 调查数据，先用人工映射拼出一张 153 列的总表，再让本地 4B 模型独立走一遍，今年又换了更强的盘古 7B 走第三条路。

【要点】

- 清洗后 185,632 行、6 个年份、200–570 列不等的宽表
- 人工路线：跨年共有列 42 → 153，重命名 382 条，取值统一 109,745 条
- 小模型路线：`qwen3.5:4b` + Ollama，得到 110 列、185,586 行
- 盘古路线：`openPangu-Embedded-7B-V1.1` 本地 GGUF 量化，判断更稳但代价高一个量级
- 今天不评"哪条路更强"，只回答"哪一段能交给模型、该交给哪个模型"

口播：这次汇报讲三种做法。第一种是已经交付的人工对齐，42 个跨年共有列扩到 153 个；第二种是本地 4B 模型独立跑完清洗和对齐，拿到 110 列；第三种是这两周新试的盘古 7B，同一条管线、同一套提示词，只换模型。前两种差 43 列，重叠部分几乎一样；第三种在 8 对边界样本上和 4B 打平，扩到 138 列才看出它把题目组拆散了，成本和兼容性也更差，我会讲清楚卡在哪。

## 02 一页看清成果

【一句话】人工路线交付了完整总表；4B 路线少 43 列，但在两边都有的 105 列上数值几乎逐格一致；盘古 7B 只推进到清洗层，8 对判定打平，扩到 138 列后题型对得上、题目组对不上。

【要点】

- 人工：153 列、185,632 行、382 条列名映射、109,745 条取值统一
- 4B：110 列、185,586 行、305 条重命名、31 个选项同义簇、5,217 条取值统一
- 重叠：105 列同名匹配，Jaccard 66.5%
- 一致：105 列非空率差 ≥1pp 的为 0 条；同主题 12 条对比里只有 2 条差 0.1pp
- 盘古：8 对判定 100% 命中，与 4B 打平，耗时中位 13.7 秒（4B 为 4.7 秒）；扩到 138 列后 kind 96.4%、group 5.1%

口播：先看总数。人工这边 153 列、18.56 万行；4B 那边 110 列、18.56 万行，行数只差 46。列数差 43，拆开看是 48 列只有人工有、5 列只有 4B 有、105 列两边都有。关键在最后这个 105：非空率差异超过 1 个百分点的，一条都没有。盘古那条线只到清洗层，8 对判断和 4B 一样，但慢三倍；扩到 138 列才看出它把题目组拆散了，后面单独讲。

## 03 手搓对齐怎么走

【一句话】先统一"题在哪一组"，再统一"列叫什么"，最后统一"选项怎么写"，顺序反了会白干。

【要点】

1. **文本归一**：大小写、全半角、弯直引号、`etc_` → `etc.`，只做确定性替换
2. **组路径重映射**：`isolate.environments.Docker` → `environments.isolate.Docker`；2019 的长问句 `what_other_language_s_do_you_use[...]` → `other.lang.*`
3. **同义词表**：`systems administration` → `System administration`；`OS-provided Python (via apt-get, yum, homebrew, etc_)` → `OS-provided Python`
4. **重名去重**：新名字撞车就回退确定性归一，再撞就加 `__dupN`
5. **取值统一**：只处理"同一选项的不同写法"，共 109,745 条
6. **取交集**：六年都存在的列才进总表，得到 153 列

口播：手搓这条路，写代码不难，难在定顺序：先归组，再改列名，最后才动取值。顺序反了，改好的名字会被后面的归一化冲掉，白干一遍。

【图】`figures/f2_mapping_scale.png`（人工 382+109,745，LLM 305+5,217）

【来源】`aligned/alignment_report.md` 重命名示例；`align_survey.py`

## 04 手搓的代价

【一句话】153 列不是一次写成的，2019 一年就改了 201 个列名，成本集中在"第一次遇到新题型"。

【要点】

- 分年重命名：2019 **201**、2020 31、2021 48、2022 43、2023 25、2024 34
- 2019 是格式最乱的一年：长问句做列名、选项挤在方括号里、大小写混用
- 2023/2024 题干改写，同义词表要跟着补（`how.involved` 的整句变体）
- 模型归并撞名 25 处（2019 九处、2021/2022 各五处、2023/2024 各三处），已回退确定性归一；最终总表仍有 15 个 `__dup` 列
- 好处：每一步都有 diff，可解释、可复现；坏处：新一年多出上百列时，第一年最费人

口播：代价也在这。2019 一年改了 201 个列名，后面五年加起来才 181 个——那年的列名是整句问句，等于没有命名规范。这套映射表是一年一年撞出来的，好处是能 diff、能回滚，坏处是明年再来新题，第一年还得人肉趟一遍。

## 05 4B 小模型怎么试

【一句话】模型不碰数据，只输出可校验的决策 JSON；候选由人工词表和数据证据给出，模型只在边界上回答"是不是同一个"。

【要点】

- **输入是画像，不是原始表**：列名、非空率、唯一值数、top 值、长度分布；自由文本列脱敏，只给长度
- **组路径三段式**：证据快对齐（选项重合 ≥0.60 且领先第二候选 ≥0.10，不问模型）→ 证据不够的逐对问"是否同题" → 剩下的从人工词表 84 条候选里选写法，缺省 `keep`
- **选项/取值两段式**：`norm_key` 确定性合并 → 候选对逐对判断 → 并查集聚簇 → 按人工词表统一写法（78 处）
- **护栏**：Yes/No 占比 ≥0.60 禁改道版本类路径、`multi_level` 与 `multi_option` 题型冲突拒合、多选取值 Jaccard <0.20 拒合、结构不得重复拼接、簇 ≤4 项且 ≤50%、删行 ≤60%、删列 ≤20%
- **缓存**：304 个决策文件，sha256 键；首次全量约 30 分钟，命中缓存 2.7 分钟
- **口径**：2023/2024 的人工映射不进提示词，只用于对账
- **结果**：20 处组路径改道、31 个同义簇、162 对判定（接受 34 对）、5,217 条取值统一
- **可换模型**：提示词、护栏、词表对盘古原样复用，只改模型名和生成预算，不动判定逻辑

口播：模型这部分，我刻意让它"只动嘴不动手"：看到的是列画像，输出的是 JSON，真正执行的是 Python。我改了一版做法：不再让模型"给标准路径"，先让代码拿证据定——某组的选项和人工某条路径重合 0.93，就直接对齐，不问模型；证据不够的才逐对问"这两条是不是同一道题"，它只答 a 或 b；剩下的在人工词表里选写法。选项和取值同理，先合并完全相同的，剩下逐对判同义，最后由词表定写法。4B 判断很稳，可一旦要它"生成"，就整组塌缩或自造路径。

【来源】`llm/README.md`；`llm/reports/alignment_report.md`；`llm/decisions/` 计数

## 06 三方对账：两条能对账，第三条只能对判断

【一句话】人工与 4B 覆盖差 43 列，重叠的 105 列数值几乎一样；盘古 7B 没走到对齐，只在判断层与 4B 打平。

【要点】

- 并集 158 = 105 匹配 + 48 仅人工 + 5 仅 4B
- 差距集中在跨年改名的题：`develop.for.cloud`（2019 叫 `run.in.cloud`）、`orm`（2019 叫 `ide.databases`）、`unittesting`、`other.purposes` 整族
- 105 个匹配列，非空率差 ≥1pp 的 **0 条**
- 同主题 12 条对比，只有 `other.lang.C/C++` 差 0.1pp（28.1% vs 28.2%）
- 行数：2021 差 23（23,201 vs 23,178）、2022 差 23（23,009 vs 22,986），其余四年一致
- 口径：2023/2024 人工映射未进提示词，105 是留出测试成绩
- 反例：`is.python.main → ide.python_version`（改造前），路径合法、六年一致，但语义是"是否以 Python 为主"；现在取值指纹护栏直接拒掉
- **第三条路的缺位**：盘古跨年对齐未产出，三方只能对到清洗列语义——8 对判定 4B 与 7B 均 100% 命中，中位耗时 4.7 秒 vs 13.7 秒；138 列的逐列比放到 08 节

口播：两边都有的 105 列，非空率没有一条差过 1 个百分点。列集合的 Jaccard 是 66.5%，剩下的差距基本都在跨年改名题上：云开发那道题 2019 叫 `run.in.cloud`，后来叫 `develop.for.cloud`，没有共同词，模型不敢并。另一种错更难发现：改造前 `is.python.main` 被六年如一日映射成 `ide.python_version`，路径完全合法，格式护栏抓不到，四个真版本列变成 `__dup`。现在这条会被"取值是 Yes/No 就不能进版本题"直接拦住。第三方这条路得说清楚：它只跑到清洗层，没跑到对齐，所以严格意义上这里只有两条线能对账，第三条只能跟 4B 比判断。8 对样本上打平；扩到 138 列，题目组那项才露出问题，下一节讲。

## 07 第三条路：盘古 7B 走到了哪一步

【一句话】同一条管线、同一套提示词只换模型：8 对边界样本打平，成本高一个量级，2019 清洗跑到 156 列按时间窗收尾。

【要点】

- **选型**：`openPangu-Embedded-7B-V1.1` Q4_K_M，4.59 GiB，8 GB 显存可全量驻留，实测 57 tok/s（100% GPU）
- **更大的档位不可行**：盘古 2.0 系列最小档 Q3_K_M 仍 40.7 GiB，本机物理内存 15.6 GB，连 mmap 都放不下
- **没有 JSON 约束**：Ollama 给 `pangu-embedded` 架构初始化不了 JSON grammar sampler，`format=json` 直接 400，只能靠提示词约束加容错解析兜住
- **没有思考链开关**：模板里根本没有 thinking 分支，`think=false` 是空操作；模型自带"先推理再回答"，每列多出约 300–400 token 的推理正文
- **成本同口径**：2019 清洗每列 407 token 对 55（7.4 倍），纯推理 6.6 秒对 0.73 秒（9 倍）；墙钟跨度 127 分钟里 112 分钟是两次调用之间的空档，不算法模型开销
- **判断层打平**：同一组 8 对样本，4B 与 7B 都 100% 命中、JSON 全部合法、跨轮一致

口播：第三条路是想看看"更大的模型会不会判得更准"。8 对边界样本上没看出来，两个都全对，JSON 也都合法。成本按决策缓存算：每列 407 token，4B 是 55，差七点四倍；纯推理每列 6.6 秒，4B 是 0.73 秒，差九倍。所以不是跑不动，是同样的活儿要多花近十倍时间，我在时间窗内跑到 156 列就收了。它一定会先写一段推理再给答案，这段关不掉，模板里没有开关；Ollama 又不给它的 JSON 约束，只能靠提示词兜格式。这两项是它贵的原因，也决定了它的位置：关键分歧点的仲裁者。

## 08 扩到 138 列：题型对得上，题目组对不上

【一句话】8 对样本换成 2019 年两侧都判过的 138 列：kind 一致 96.4%，option 71.0%，group 只有 5.1%。

【要点】

- **口径**：只读两侧决策缓存，按原始列名对齐、同一列取最新一条，只比两侧都判过的列，未覆盖的不进分母
- **kind 96.4%（133 列）**：差的 5 列全是「Other 自由文本」被 7B 判成 multi_option
- **option 71.0%（98 列）**：差的 40 列里，25 列只差大小写（`Apache Spark` 对 `apache spark`），8 列是写法，7 列单侧留空
- **group 5.1%（7 列）**：138 列上 4B 给 40 个组名，7B 给 91 个，多选题的选项本该共用一个组
- **不是批次太小**：4 列一批的 109 列一致率 6.4%，1 列一批的 21 列全 0%，方向正好相反
- **只发生在 2019**：2020 表头自带组路径，`other.lang`、`other.purposes` 各 5 列都是 5/5 同组
- **一个例子**：Big Data 工具那道题 9 个选项，4B 归 1 个组，7B 拆成 8 个（`bigdata`、`apache.spark`、`apache.tez`、`clickhouse` 各成一组）

口播：8 对样本太少，两个模型都全对，说明不了什么。所以我把 2019 年两个模型都判过的 138 列拿出来逐列比。题型基本一致，96.4%，差的那 5 列全是"Other 自由文本"被 7B 判成多选。选项名 71%，差的里面一大半只是大小写，`Apache Spark` 对 `apache spark`，算不上语义错。真正的问题在题目组：138 列上 4B 给 40 个组，7B 给 91 个。Big Data 那道题 9 个选项，4B 归成一个组，7B 拆成八个。我一开始怀疑是批次太小、模型看不到同一道题的兄弟列，结果反过来了：4 列一批的列一致率 6.4%，1 列一批的全 0%。而且这个问题只在 2019 出现。2020 起的表头自带组路径，我抽的两个前缀各 5 列都是 5/5 同组。根子在 2019 的表头长成「选项: 问句」，没有锚点可抄，代码只能用问句多数票兜底，组名退化成某个选项名，跨年对齐时这个锚点就弱了。

## 09 结论与下一步

【一句话】交付继续走人工映射；4B 用来出候选、做交叉核对、写解释；盘古暂时只做分歧仲裁，不进主线。

【要点】

- **人工**：确定性强、可解释、可复现；成本在映射表维护，2019 年一次 201 条
- **4B**：逐对判断（同题、同义）可用，长题干和新列名的语义判断可用；一旦要求"生成"标准路径或整组聚类就不可用；组路径仍会犯"结构合法、语义错误"的错，靠取值指纹兜
- **盘古 7B**：8 对判断未见提升，138 列上题型对得上（96.4%）而题目组对不上（5.1%）；每列 token 7.4 倍、缺 JSON 约束、关不掉推理；适合对少数高风险判断做二次确认
- **下一步**
  1. 给跨年改名题补名称证据（`develop.for.cloud`、`orm`、`unittesting` 仍判 `keep`）
  2. 被拒映射进人工确认队列，确认后写回规则管线映射表
  3. 统计与图表跟着对齐产物自动重跑
  4. 若继续评估盘古，先解决 2019 的组路径锚点与推理正文抑制这两件事，再谈扩量
- **边界**：叙述可以让模型润色，数字必须回到 CSV

口播：所以三条路的定位不一样。人工那条继续交付；4B 这条用在新一年的候选映射、对账的第二双眼睛、以及把差异写成解释；盘古这条暂时只在几个高风险判断上做仲裁。它最不能信的，恰恰是它写得最顺的那部分：parity 报告里模型自己写"规则管线更可信"，论据是"开发环境类信息更少"——可 `environments.isolate` 三列里两列都在，它只是猜。叙述可以交给模型，数字必须回到 CSV。

## 附录 A：可能被追问的六个问题

**1. Jaccard 只有 66.5%，为什么还说两条线一致？**

Jaccard 衡量列集合重叠，不衡量同名列的取值。剩下 43 列的差距集中在跨年改名的题（`develop.for.cloud`、`orm`、`unittesting`）和个别选项写法上，不是算错。一致性要看交集：105 个同名列，非空率差 ≥1pp 的 0 条。

**2. 非空率差是怎么算的？分母是什么？**

逐列算非空单元格占该年总行数的比例，再取两年差值的绝对值。2021/2022 两边行数各差 23，但没有把任何一列推过 1pp。

**3. 5,217 条取值统一，是不是虚高？**

这个数字数的是受影响的单元格，与人工那 109,745 条同口径。去重后只有 25 条不同映射，其中 21 条是版本号字形归一（`Python 2.3` → `Python 2_3`），真正的词义归并是 `Eclipse with PyDev → Eclipse + Pydev` 这一类。汇报时说"5,217 条单元格"比说"5,217 条映射"准确。

**4. 2021/2022 各差 23 行，差在哪？**

LLM 多删了 23 条重复行：2021 删 438 条、人工删 415 条；2022 删 302 条、人工删 279 条。具体是哪一列参与去重导致的口径差，还没追到列级，先记为待查。

**5. 明年再来一版数据，先做哪一步？**

先跑 LLM 出组路径候选，再人工审 diff。三段式的顺序不要改：先让代码拿证据定，剩下的才问模型，问也只让它答"是不是同一个"；也不要直接采信模型写的差异解释。

**6. 盘古比 4B 强在哪？为什么不让它跑全量？**

8 对边界样本上两者都是 100%，看不出强弱。扩到 2019 的 138 列，差别出来了：kind 一致 96.4%，option 71.0%（差的 40 列里 25 列只是大小写），group 只有 5.1%——4B 给 40 个组名，7B 给 91 个，基本按选项各造一个。2020 起的表头自带组路径，同一个探针在两个前缀上都是 5/5 同组，所以这是 2019 的问题，不是模型到处都错。成本按决策缓存同口径算：每列 407 token 对 55，纯推理 6.6 秒对 0.73 秒，墙钟跨度里近九成是调用之间的空档，不算模型开销。它现在的定位是对少数高风险判断做二次确认；真要扩量，先把 2019 的组路径锚点和推理正文抑制解决掉。
